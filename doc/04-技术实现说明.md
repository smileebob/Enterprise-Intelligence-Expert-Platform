# 技术实现说明

> 本文档说明 AngentPlatform 的关键算法、技术架构、数据来源、外部依赖、运行方式、测试结果与当前限制。
> 完整实现细节以仓库代码与自动化测试为准。

## 一、关键算法与模型

### 1.1 KP-1 知识管道（差异化核心）

针对企业知识治理中的核心问题「外部知识覆盖内部专有知识」，平台实现了完整的知识管道：

```
解析切分 → 结构感知切分 → citation_id 映射 → 六级打标 → 敏感扫描
→ 入库（异步任务 + 幂等）→ 混合检索（0.6 向量 + 0.4 全文）
→ 分区召回 + 权限过滤 → 融合与冲突消解 → 可追溯引用装配 → 关联遍历
```

- **六级信息分级**：原始材料 / 内部专有 / 外部通用 / 当事方陈述 / AI 推断 / 人工确认；
- **融合优先级全序**：`confirmed ≥ internal > stated > external > ai_inferred`——内部实测优先于外部普遍结论；
- **冲突检测**：主题词命中且双方（如内部 vs 外部）在场时登记冲突，**双方保留、显式标注**，不默默采信；
- **合规例外（CS-05）**：法规 / 安全 / 合规场景以权威外部标准优先，由**确定性规则表**执行（`core/knowledge/compliance.py`），任何版本不下沉给大模型裁决；
- **混合检索**：向量（pgvector HNSW / SQLite 侧 Python 算分）与全文（tsvector / jieba 分词）按 0.6/0.4 加权，分区与权限过滤下推到存储适配器。

### 1.2 六维评估引擎

- 打分器注册表 + 领域插件公式（化学 D1–D6，采用六维评分参考实现公式；金值对拍见 `tests/test_phase6_evaluation.py`）；
- 场景权重画像 5 类 + 领域标准层（`eval_standard` 版本化，BR-09 回溯）；
- **规则 + 大模型分工**：规则引擎打基线分，大模型处理边界案例——校准协议 **±10 限幅、偏差 >15 转人工、JSON Schema 双重校验、失败降级为规则分**；
- 双层护栏（BR-05 四档置信标注 + D4 参考级）+ 置信度三因子。

### 1.3 自研状态图编排引擎

- 节点 / 条件边 / interrupt / resume / 检查点落库 / 重规划（≤2 次），接口同构 `run_turn / resume`，收敛单点、可平滑替换为 LangGraph 等框架；
- 状态流：输入 → 澄清（槽位缺失即 interrupt 追问）→ 规划 → 检索 → 融合 → 工具 → 评估 → 生成 → 自检 → 重规划 → 输出 → 记忆写入；
- **SSE 流式协议**：step / citation / token / eval / done / error 六类事件，**先校验后外发**（输出 Hook 通过才推流）。

### 1.4 模型网关与降级体系（不训练任何模型）

- `openai_compat` 适配器：百炼（qwen）/ Ollama / vLLM 等 OpenAI 兼容端点，密钥仅环境变量注入；超时 / 失败重试（tenacity）+ 熔断（pybreaker）；
- `offline` 确定性通道（默认）：SHA256 哈希嵌入 + 规则组装，**零云依赖完整演示**，测试与验收全部可复跑；
- `replay` 通道：预录向量回放，界面显著标注「离线回放」（**仅用于演示与可复现，不是完整执行回放**，见 §七）；
- 降级层级 L0–L4（网关重试熔断 → L3 纯全文检索等），响应 `meta.degrade_level` 与前端徽标显式呈现。

### 1.5 安全与治理（五类 Hook）

输入（注入检测 + PII 脱敏 + 越权预检）/ 检索（权限分区注入，SQL 下推）/ 工具（RBAC + 危险二次确认 + 限流 + 审计）/ 输出（引用存在性校验 + 脱敏 + 合规提示 + 低置信标注）/ 记忆写入（置信度门槛 + 防污染）。

BR-08 角色动态脱敏规则表在**界面 / API / 日志三处口径一致**；全程 `trace_id` 可复原任一回合。

### 1.6 记忆与自成长

- 四层记忆：会话级滑窗 / 用户级提取 / 企业级注入 / 领域级约束；个人 → 企业晋升（≥2 用户同向 + 管理员确认）；衰减与压缩周期任务（BR-07）；
- PIPL 合规：个人记忆查阅 / 更正 / 删除 / 导出，owner 强校验，全程留痕；
- 自成长闭环：反馈（采纳 / 修正 / 否决）→ 正负样本 → 案例库 / 纠错规则 → 标准草稿审核发布；标注数据导出接口（P2 预留）。

## 二、技术架构

### 2.1 总体形态：通用底座 + 可插拔领域插件

```
┌─────────────────────────────────────────────────────────┐
│  platform-web（Vue 3 + Element Plus 独立工程）            │
│  对话台(SSE/思考步骤/引用角标) │ 评估卡 │ 装配台 │ 审计台     │
└──────────────────────────┬──────────────────────────────┘
                           │ REST /api/v1 + SSE
┌──────────────────────────▼──────────────────────────────┐
│  app/ FastAPI 应用（create_app 工厂 + APIRouter 业务域）    │
│  auth/chat/knowledge/evaluation/memory/domains/           │
│  governance/growth/ops                                   │
├─────────────────────────────────────────────────────────┤
│  core/ 通用底座（领域无关）                                 │
│  abstraction(六接口) │ knowledge(KP-1) │ orchestration    │
│  memory(四层) │ evaluation(六维) │ gateway(工具权限)      │
│  guardrails(五Hook) │ growth(自成长) │ admin(装配)        │
├──────────────────────────┬──────────────────────────────┤
│  domains/ 领域插件        │  adapters/ 运行时适配器         │
│  ├ chemical（完整实例）   │  storage_pgvector / sqlite     │
│  └ investment（轻量实例） │  model_gateway / blob / repos  │
├──────────────────────────┴──────────────────────────────┤
│  PostgreSQL 16 + pgvector │ Valkey(缓存/锁/broker) │ Celery │
└─────────────────────────────────────────────────────────┘
```

### 2.2 模块清单（M0–M9）

| 模块 | 能力 | 落位 |
|---|---|---|
| M0 抽象层 | 六接口（Knowledge / Memory / Eval / Audit / Blob / ModelGateway） | `core/abstraction`、`adapters` |
| M1 知识底座 KP-1 | 见 §1.1 | `core/knowledge` |
| M2 编排引擎 | 见 §1.3 | `core/orchestration` |
| M3 记忆中心 | 四层记忆、晋升、衰减、PIPL | `core/memory` |
| M4 评估引擎 | 见 §1.2 | `core/evaluation`、`domains/*/evaluation` |
| M5 工具权限网关 | MCP 同构 @tool、RBAC、危险确认、限流、审计 | `core/gateway` |
| M6 安全 Hook | 见 §1.5 | `core/guardrails` |
| M7 自成长 | 见 §1.6 | `core/growth` |
| M9 平台管理 | 领域装配（五要素校验 / 发布 / 回滚）、角色权限、审计、冲突裁决 | `core/admin`、`app/domains`、`app/governance` |

### 2.3 工程规范（节选）

应用工厂 + APIRouter 按业务域拆分；统一响应 `{code, message, data}` 与集中错误码；写接口幂等（Idempotency-Key + SETNX / 唯一索引）；DTO 与 ORM 分离；JWT（OAuth2PasswordBearer）+ argon2；slowapi 限流 + CORS 白名单 + 安全响应头；JSON 结构化日志 + X-Request-ID 贯穿；`/healthz` `/readyz` `/metrics`；Alembic 迁移；UTC 存储。

工程规范的具体配置与门禁见 `platform/pyproject.toml`、`platform/tests/` 与 CI 配置。

## 七、当前限制

1. **数据**：当前全部使用演示模拟数据（已显式标注），未经受真实数据量级与分布检验；真实业务数据接入路径已明确（解析适配器扩展 + 标准层校准）。
2. **招商领域**：外部数据源（工商 / 专利 / 投融资）未实时接入，企业发现以预置库演示能力范式；实体消歧为已知后续难点。
3. **多模态**：当前覆盖文档 / 表格 / 结构化 JSON，图片与仪器图谱解析为后续里程碑。
4. **模型**：不训练模型；`live` 模式回答质量取决于所接大模型，`offline` 模式为确定性兜底（L1 简化分析）。
5. **规模**：单机 Compose 起栈为参考部署形态；生产化扩展（读写分离、检索下推、worker 水平扩展）需结合真实负载设计。
6. **配方性能预测**（延伸方向）未训练专用回归模型，已预留插件点——三个延伸方向（配方优化 / 清洗切换优化 / 缺料预警）的逐方向实现路径与平台扩展点见 [doc/01-化学领域场景说明.md](01-化学领域场景说明.md) §六。
7. **执行回放**：模型网关的 `replay` 仅回放预录向量；提示词、检索结果、工具调用与模型输出尚未形成统一 append-only 事件日志，完整执行回放 / 分叉在路线图中（见根 README §十二）。
8. **领域插件边界**：编排引擎的「评估对象装配」仍有化学领域专用逻辑（`_node_plan`、`_assemble_object_ref`、`_save_solution`），尚未完全下沉到领域插件，正在持续抽象。
