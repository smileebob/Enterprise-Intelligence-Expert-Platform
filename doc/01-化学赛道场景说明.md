## 一、官方赛题还原（已核验）

### 1.1 业务背景

传化功能化学深耕**纺织印染助剂**领域，为客户提供化学产品、应用技术及专业解决方案。由于客户在面料类型、加工工艺、生产设备及目标性能等方面存在差异，业务呈现**需求高度个性化、产品品类复杂、专业服务依赖专家经验**的特点。核心业务链路：研发（配方设计、实验验证、工艺优化）→ 生产（多品类柔性制造）→ 供应链（采购、排程、交付）→ 销售与服务（产品匹配、技术指导、现场试样、售后支持）。

### 1.2 重点推荐场景：AI 化学家（销售与服务）

客户经常提出柔软度、防水性、耐洗性等个性化需求。技术工程师需要综合查阅产品资料、历史试样报告、工艺文件及外部文献，依靠专业经验完成产品选型与应用方案设计。官方建议构建面向纺织化学行业的 AI 化学家智能体，探索三大能力：

| # | 官方能力要求 | 内涵 |
|---|---|---|
| ① | **专业需求理解** | 通过自然语言交互与多轮问答，理解客户需求，识别面料类型、目标性能及关键工艺条件 |
| ② | **专业知识检索与融合** | 智能检索企业内部产品、配方、工艺及实验知识，按需整合外部专利、文献及行业资料，形成**准确、可追溯**的专业回答 |
| ③ | **解决方案辅助生成** | 结合产品知识及历史应用案例，辅助推荐适用产品、应用工艺及后续实验验证方向，形成初步客户解决方案 |

### 1.3 官方点名的五大业务痛点

1. **客户需求理解困难**——客户描述往往不够专业或完整，难以快速转化为标准化技术需求；
2. **专业知识分散、难以复用**——大量产品资料、实验报告和应用案例以非结构化形式存储，跨文档查询与知识关联困难；
3. **内外部知识融合不足**——外部知识引入后容易**覆盖企业内部专业知识**，难以根据问题合理选择与融合知识来源；
4. **复杂知识理解能力有限**——现有 AI 工具偏向信息检索与内容拼接，缺乏跨文档分析、专业知识重组及深度推理能力；
5. **方案生成依赖专家经验**——产品、配方、工艺及客户应用效果之间关系复杂，难以快速复用历史经验形成解决方案。

### 1.4 官方智能体问题示例

- 产品选型：某客户希望改善织物柔软度，同时保持耐洗性能，应如何匹配现有产品并提出初步应用建议？
- 内外部知识融合：如何结合企业内部产品资料和外部专利文献，分析某类功能性整理助剂的适用性及技术发展方向？
- 实验分析与优化：如何综合多份历史试样报告，识别影响产品应用效果的关键因素，并提出后续验证建议？

### 1.5 其他创新方向（平台已预留扩展，实现路径见 §六）

AI 辅助纺织助剂配方优化、AI 驱动的生产设备清洗切换优化、AI 驱动的关键原材料缺料预警。三个方向均未在本期 Demo 中实现，但平台底座已为各自预留了明确的扩展点，**§六给出逐方向的实现路径与方案**。

## 二、痛点 → 能力 → 平台实现映射

本作品以「**通用底座 + 可插拔领域插件**」的企业级领域专家 Agent 平台承载化学赛道，AI 化学家为**主领域（完整五要素插件）**。五大痛点逐条映射：

### 痛点 1：客户需求理解困难 → 编排引擎「澄清槽位」机制

- **实现**：自研状态图编排引擎（`core/orchestration`），在「规划」前设置**澄清节点**：领域插件声明各意图模式的必填槽位（化学领域如面料类型、目标性能、工艺条件），缺失即触发 `interrupt` 追问，用户补充后经独立 `resume` 接口恢复执行；
- **演示**：提问「帮我做防水整理」→ 平台追问面料与耐洗要求 → 补充「涤纶面料，要防水耐洗 50 次」→ 输出完整方案；
- **对应官方能力 ①**。

### 痛点 2：专业知识分散难复用 → KP-1 知识管道（多模态知识底座）

- **实现**：产品技术说明、配方、工艺文件、历史试样报告、实验数据统一经「解析切分 → 结构感知切分 → citation_id 映射 → 六级打标 → 敏感扫描」入库；混合检索（**0.6 向量 + 0.4 全文**）+ 分区召回，支持跨文档关联遍历（`kb_relation`）；
- **效果**：跨文档查询一次问答完成，每条结论携带可点击溯源的引用角标；
- **对应官方能力 ② 的"检索"半区**。

### 痛点 3：内外部知识融合不足（官方核心痛点）→ 六级信息分级 + 融合冲突消解

这是本作品**差异化最强的能力**，也是与朴素 RAG 拉开差距的地方：

- **六级信息分级**：知识按可信度分六层打标——原始材料 / 内部专有 / 外部通用 / 当事方陈述 / AI 推断 / 人工确认；
- **融合优先级全序**：`confirmed ≥ internal > stated > external > ai_inferred`，**内部实测永远优先于外部普遍结论**，从机制上保证外部知识不覆盖内部专有；
- **冲突检测与标注**：内外部结论不一致时**双方保留、显式标注**（如 CS-01：内部实测耐洗 50 次 vs 外部文献普遍结论），而非默默采信一方；
- **合规例外（CS-05）**：涉及法规/安全/合规时以**权威外部标准优先于内部声明**，由确定性规则表执行（`core/knowledge/compliance.py`），不下沉给大模型裁决——如出口欧盟面料询用 C6 有机氟产品时，强制合规提示并推荐无氟替代；
- **对照证据**：反朴素 RAG 对照实验 **5/5 vs 0/5**（同一批冲突场景，朴素 RAG 全部采信错误或单方结论，平台全部正确标注）；
- **对应官方能力 ② 的"融合"半区与官方能力 ③**。

### 痛点 4：复杂知识理解能力有限 → 状态图编排 + 跨文档推理链

- **实现**：编排引擎按「澄清→规划→检索→融合→工具→评估→生成→自检→重规划（≤2 次）→输出」状态图执行，支持多步推理与反思重规划；前端**思考步骤时间线**全程可见（检索了什么、融合时遇到什么冲突、调用了哪个工具），而非黑盒拼接；
- **演示**：提问「综合分析多份试样报告，影响 TF-WR 系列防水效果的关键因素是什么」→ 平台跨文档检索→融合→给出带引用的因素分析。

### 痛点 5：方案生成依赖专家经验 → 六维评估引擎 + 自成长闭环

- **六维评估**：对生成的解决方案按化学领域 D1–D6 六个维度加权打分（场景权重画像 5 类），规则引擎打基线分 + 大模型校准（±10 限幅、偏差 >15 转人工、降级为规则分），评分**可解释、可追溯**，护栏分档标注（BR-05，参考级结果显式提示）；
- **自成长闭环**：专家对结果「采纳 / 修正 / 否决」→ 正负样本回流案例库与纠错规则 → 领域标准草稿经审核发布（BR-09，不自动重算）→ 平台越用越聪明，专家经验从个人大脑沉淀为组织资产；
- **四层记忆**：会话级 / 用户级 / 企业级 / 领域级，专家个人偏好经「≥2 人同向 + 管理员确认」晋升为企业记忆；
- **对应官方能力 ③**。

### 映射总表

| 官方痛点 | 平台机制 | 代码落位 | 验证方式 |
|---|---|---|---|
| 需求理解困难 | 澄清槽位 + interrupt/resume | `core/orchestration` | 演示路径 ③、契约测试 |

## 三、评委可操作演示路径（约 5 分钟）

> 前置：`docker compose up -d --build` + `python scripts/init_demo.py`，或本地零云依赖模式（见根 README §五）。演示账号 `expert / Expert@12345`。

1. **内外部知识融合（核心亮点）**：对话台选择「AI 化学家」→ 提问「客户要涤纶面料做无氟防水，要求耐洗 50 次不明显下降，无氟能做到吗？」→ 观察**思考步骤**（检索/融合/冲突标注）与**逐条引用角标**（CS-01：内部实测 vs 外部普遍结论，双方保留显式标注）。
2. **合规强制提示（CS-05）**：提问「客户做出口欧盟的户外面料，要高性能防水，能用我们的 C6 有机氟 TF-WR-6612 吗？」→ 观察**合规强制提示**（法规优先于内部声明）+ **无氟替代推荐（TF-WR-6608）** + 评估事件中 **D6 ≤ 30 的维度反转**。
3. **澄清追问（需求理解）**：提问「帮我做防水整理」→ 平台**追问面料类型与性能要求** → 补充「涤纶面料，要防水耐洗 50 次」→ 获得完整方案。
4. **六维评估与自成长**：右侧评估卡查看六维得分/权重/依据/护栏标注（BR-05 参考级）→ 点「采纳」→ 知识管理员审核正样本案例入库、专家个人记忆出现该偏好（PIPL 可查/改/删/导出）。
5. **量化回归（可选）**：`python scripts/run_regression.py` → 8 问引用命中率、CS-01~05 判据、反朴素 RAG 对照报告（输出 `_tmp/regression_report.md`）。

## 四、数据说明（合规重点）

- 初赛阶段无真实业务数据，全部演示数据为**赛事模拟数据**：产品名/型号/专利号/DOI/数值均虚构，界面与 API 响应中以 `is_mock` 显式标注；
- 模拟数据集构成（数据文件位于 `platform/data/mock/`）：产品与工艺知识、配方、实验/试样记录、外部专业知识（论文/专利/标准）、业务问答样例，**内置 5 个冲突场景**（CS-01~05）专门用于验证融合与合规机制；
- **终赛真实数据对接路径**：官方数据（产品与工艺知识 / 实验与应用案例 / 外部专业知识 / 业务问答样例）与本平台知识入库管道的输入形态一致——按现有解析适配器扩展对应 schema 即可灌入，六级打标、分区召回、评估标准层均为数据无关的通用机制，预计对接工作集中在「解析适配器新增 + 领域标准层校准」两处。

## 六、官方三个创新方向的实现路径（平台扩展预留实证）

官方在重点推荐场景之外"同样关注"三个创新方向。本节说明：**平台哪些机制已被直接复用（均有代码落位）、每个方向需新增什么、分几步落地、如何验证**。三个方向共用同一结论——新增边际成本主要是「数据 + 少量领域代码包」，底座（六级分级、编排、评估、Hook、审计）零改动。

### 6.1 AI 辅助纺织助剂配方优化

> 官方描述：整合历史配方与实验结果，辅助推荐候选配方并预测关键性能。

**平台已预留（可直接复用）**：

| 复用点 | 代码落位 |
|---|---|
| 配方/实验数据基座：结构化表 + 知识块双承载，入库管道已支持 formulas / experiment_cases 两类知识 | `domains/chemical/models.py`（chem_formulas / chem_experiments）、`domains/chemical/ingest_adapter.py` |
| 配方与实验检索工具（已上线，MCP 同构契约） | `search_formulas` / `search_experiments`（`domains/chemical/toolset.py`） |
| 候选方案打分排序：六维评估引擎 + 打分器插件点（纯 Python 函数，按 `chemical.d1_performance` 约定动态解析） | `core/evaluation/engine.py`、`core/domains.py: resolve_scorer`、`score_solution` 工具 |
| "预测值"的可信度承载：六级信息分级中 `ai_inferred` 级，预测结果天然带分级标注进入融合与引用 | `core/knowledge`（六级打标与优先级全序） |
| 实验结果回流：候选配方的试样验证 → 案例库/纠错规则 → 标准层版本化 | `core/growth` 自成长闭环 |

**需新增**：① 配方候选生成器——初版采用「相似配方检索 + 成分约束规则」的确定性生成（规避生成式杜撰风险），不做自由文本生成；② 性能预测回归模型（P2 训练点，成分 → 关键性能）——平台 ModelGateway 与打分器插件点已预留挂接位置，预测分作为 D1 性能达成度的输入之一，以 `ai_inferred` 分级注入，经人工确认（`confirmed`）后方可晋升。

**实现路径**：阶段一（规则 + 检索，模拟数据）：相似配方检索 → 成分约束过滤 → 六维排序 → 输出候选配方与依据引用；阶段二（终赛真实数据）：训练性能预测回归模型，回测达标后接入评估链；阶段三（实验闭环）：试样结果回流 chem_experiments，自成长机制持续修正候选生成规则。
**验证方式**：历史数据留出法回测（用旧配方预测已发生的新实验结果，看命中率）+ 专家盲评候选配方可用率。

### 6.2 AI 驱动的生产设备清洗切换优化

> 官方描述：优化生产顺序与设备切换，减少清洗消耗和停机时间。

**场景本质**：带约束的排产优化（换产兼容矩阵 × 订单交期 × 设备产能）。关键架构决策——**不让 LLM 直接算优化**，采用「Agent 编排层 + OR 求解器计算层」的神经符号混合架构：LLM 负责把自然语言需求翻译成约束参数、调用求解器、解释结果；求解器负责精确求解。

**平台已预留（可直接复用）**：

| 复用点 | 代码落位 |
|---|---|
| 求解器可注册为领域工具：@tool 契约 + RBAC + 限流 + 全量审计 + 危险操作二次确认，开箱即用；契约注明"生产可桥接 MCP server" | `core/gateway/registry.py`、`domains/chemical/tools/chemical_tools.yaml` |
| 长耗时求解任务化：Celery 队列异步执行，接口立即返回任务 ID | `core/celery_app.py`（B-06） |
| 对话式编排：需求理解 → 参数抽取 → 调用工具 → 解释生成的链路即现有状态图 | `core/orchestration` |
| 换产/清洗规则（如浅色→深色免洗规则）作为领域知识入库、六级打标、可追溯引用 | KP-1 知识管道 |

**需新增**：① 数据：换产兼容矩阵、设备产能、订单与交期表（新领域表 + 入库适配器 schema 扩展，同现有适配器模式）；② 求解器工具：OR-Tools CP-SAT（Apache-2.0）封装为 @tool，输入约束参数、输出排产方案与清洗次数/停机时长；③ 解释生成：将求解结果翻译为可执行生产指令与调整原因。

**实现路径**：阶段一（模拟数据 PoC）：对话提问"这批订单怎么排清洗最少"→ 参数抽取 → CP-SAT 求解 → 方案 + 解释；阶段二：接入 MES/ERP 真实排产数据，方案人工确认后回写执行；阶段三：滚动排产——周期任务每日重算，异常插单自动重排并解释变更影响。
**验证方式**：与人工排产对照（清洗次数、停机时长、准时交付率三项指标并行对比）。

### 6.3 AI 驱动的关键原材料缺料预警

> 官方描述：预测关键原材料缺料风险，提前生成采购预警与补货建议。

**平台已预留（可直接复用）**：

| 复用点 | 代码落位 |
|---|---|
| 周期任务骨架：Celery beat_schedule 已有 crontab 范例（memory-maintenance，每周一 03:00），新增"缺料扫描"周期任务零框架改动 | `core/celery_app.py: beat_schedule` |
| 库存/采购/消耗数据入库：结构化 JSON 直导适配器模式可扩展新 schema | `domains/chemical/ingest_adapter.py` |
| 缺料风险分级：打分器插件点实现"风险评分"（库存覆盖天数 × 采购提前期 × 供应商可靠性），复用评估引擎的护栏与校准机制 | `core/evaluation` 打分器注册表模式 |
| 预警处置链：预警即知识块（可追溯引用）、全量审计留痕、高危预警走工具危险确认机制推送人工；采购偏好与供应商表现可入企业级记忆 | `core/knowledge`、`core/gateway` 危险确认、`core/memory` 企业级 |

**需新增**：① 数据：库存快照、配方用量（BOM）、采购提前期、消耗速率表；② 预测逻辑：初版规则式（库存覆盖天数 < 采购提前期 + 安全库存 → 分级预警），P2 可训练需求预测模型并以 `ai_inferred` 分级注入；③ 预警实体与通知接口（工单/消息推送）。

**实现路径**：阶段一（规则预警 + 对话查询）："下个月 TF-WR 系列原料够吗？"→ 检索库存与用量 → 规则判定 → 预警与补货量建议；阶段二：接入 ERP/WMS 真实库存与在途采购，周期扫描生成预警工单；阶段三：需求预测模型 + 自动补货建议单（人工审批后执行）。
**验证方式**：历史缺料事件回放（预警命中率 / 误报率）+ 与人工盘点预警时效对比。

### 6.4 三方向共用的扩展公式

```
新场景 = 现有底座（KP-1 + 编排 + 评估 + Hook + 审计，零改动）
       + 领域数据（新 schema 入库适配器，沿用现有模式）
       + 少量领域代码包（打分器函数 / @tool 工具 / 提示词资产，按插件约定注册）
```

这正是本作品「通用底座 + 可插拔领域插件」架构对评审维度 04（工程化潜力与规模扩展）的直接回答：**不仅换领域（化学→招商）成立，同领域加场景（选型→配方/排产/预警）同样成立**。
